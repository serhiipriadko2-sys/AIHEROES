# Рубежи Искры — боевой визуальный проход: «Янтарный авангард»

Status: IMPLEMENTED_PENDING_VERIFICATION. Read the dated receipt for the final tested scope.
Scope: existing live GridRulesV2 presentation and its primary battle HUD. No combat-rule or save-schema change.

## Что меняется для игрока

Вместо шаров, кубов и цилиндров — шесть оригинальных фигурок: ополченец с щитом и копьём,
разведчик с луком и колчаном, волк, разбойник с коротким мечом, налётчик с топором,
каменный страж с янтарным ядром. Одна фигурка представляет отряд; точное число бойцов показано рядом.
Потери уменьшают число бойцов, а не растягивают и не сжимают фигуру.

На боевом экране: русские названия, портреты этих же моделей, количество бойцов,
здоровье, полосы здоровья, роль и инициатива. A1/A2 — свои отряды, B1/B2 — противник.
Буквы и форма подставок дублируют цвет: союзные подставки круглые, вражеские квадратные.
Нижняя строка объясняет текущее действие. Пауза, скорость, быстрое завершение и возврат
на карту используют прежние команды и зоны нажатия.

Фигуры поворачиваются вдоль своего пути. Ближний удар — короткое движение всей фигуры,
дальний выстрел разведчика — отдельный декоративный снаряд до момента попадания.
Это простая анимация объектов, НЕ скелетная ходьба и НЕ полноценная анимация рук/лука.

## Art source and import

- `Tools/build_amber_units.py`: Blender authoring script, refuses existing output directory.
- `ArtSource/AmberVanguard/AmberVanguard.blend`: editable original geometry.
- Six FBX meshes and six transparent 256x256 PNG portraits generated from the SAME meshes.
- Source total: 1,962 triangles across six meshes; this is not a frame-time or Android performance claim.
- `Tools/import_amber_units.py`: creates new packages only after checking source hashes and destinations.
- Destination: `/Game/AmberMarch/Units`, isolated from the first map-art kit.
- Palette slots are mapped by material name, not arbitrary import order.
- All art is generated by project scripts; no extracted Heroes III / HotA assets or external character meshes.

## Read-only presentation contract

`AIHeroesBattleArt` selects presentation assets and localized display names. It never selects combat actions.
`AIHeroesLiveBattleStage` still consumes one already-produced GridRulesV2 receipt at a time.
The HUD reads `GetPresentedArmy`, not the simulation's next resolved frame. During the approach/flight,
health remains unchanged until the existing 45%-of-action impact point; fast-finish commits the same receipt once.
The health-bar denominator is the group's initial HP for this battle, not a fabricated maximum or forecast.
A model's skin/palette is preserved on damage; impact changes only the side marker.
No new actor collision can affect target selection, cell occupancy, movement cost or damage.
Loading art, portrait drawing and camera orbit never grant model readiness or perform inference.

## Compatibility

Existing action IDs 100..103 and hit rectangles stay unchanged.
The original debug status and `GetArmyStatus` remain available for diagnostic callers and replay contracts.
Long floating debug text is replaced with compact stable group tags; old tests are updated to assert this
new visible contract, while numeric health/initiative are tested through the read-only presentation roster.
Historical V2 replays share the figures, but their legacy surrounding HUD is not fully redesigned here.
Unknown unit assets have no path mapping. A missing known asset retains the prior basic-shape fallback.
Packaging/cooking of dynamically loaded assets is a separate gate; Editor success is not packaged-game success.

## Verification plan

Five new `AIHeroes.Visual.Battle` groups:
1. Six distinct imported meshes, palette assignments, bounded geometry and six portrait assets.
2. 56 roster-layout cells, valid bounds, no overlap and stable distinct group codes.
3. Actual impact timing, no premature HUD damage, fixed model scale, stable palette and external-state invariance.
4. Repeated decoration/application without duplicate components and disposal cleanup.
5. Ranged projectile visibility, pause freeze, no independent damage and cleanup at fast finish.

The existing whole-project automation suite must pass on a source/DLL-bound build.
Real graphical scenarios: Victory, Defeat, TwoGroups at 1280x720; TwoGroups at 640x720.
Capture START, PAUSED, 2X, RESULT, RETURN, DOSSIER and inspect representative actual frames.
Asset hashes and all existing player-save hashes must be unchanged during the final run.
The automated scenario is not a manual-input, visual-accessibility or gameplay-balance acceptance.
